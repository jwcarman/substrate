# Substrate documentation site — design

## Intent

Substrate has no documentation site. Its README (620 lines) is the only manual. The owner wants
"a very professional, well written documentation site", in the family of his other libraries'
sites (who, codec, occlude, nessy: MkDocs Material on GitHub Pages). Odyssey, which is built on
Substrate, gets its own site next; the odyssey site will link here for backends rather than
repeat them, so this site must be the authoritative place for everything about backends.

Success: someone evaluating or adopting Substrate, or a coding agent working for them, finds a
complete, accurate, well-written manual — what each primitive is for and how it behaves, how to
choose, configure and operate each backend, how to test, and how to secure data at rest — and
never needs to read the source to answer an ordinary question.

## Goals

- A published site at `https://jwcarman.github.io/substrate/`, built by a GitHub Actions
  workflow and deployed to GitHub Pages.
- Content that goes beyond the README (option B, chosen by the owner): new pages for each backend,
  choosing a backend, testing, and operating in production, alongside the README's material
  reorganised and edited.
- Every factual statement verified against the code at the current `main` (0.10.0 released,
  0.11.0-SNAPSHOT or later in progress): class names, method signatures, property names and
  defaults, which backend provides which primitive, TTL behaviour.
- Agent-readable: `llms.txt`, `llms-full.txt` and Markdown copies of pages (mkdocs-llmstxt), and
  a `context7.json` that points Context7 at the site's sources.
- Javadoc published under `/api/` beside the guides, as codec does.

## Non-goals

- No changes to Substrate's code or behaviour. If writing a page reveals a bug or an API that
  cannot be explained well, note it for the owner; do not fix it in this work.
- No versioned docs (one site, tracking the latest release; the changelog covers differences).
- No blog, no marketing landing page, no custom domain.
- Odyssey's site (separate design, next).

## Anti-goals

- Documenting what the code does not do. A page that states a guarantee a backend does not give
  (ordering, durability, TTL precision, delivery semantics) is worse than no page. When the code
  does not make a guarantee clear, say what is and is not promised, or leave it out.
- Padding: backend pages that are the same template with the name swapped. Each says what is
  actually particular to that backend.
- Describing `main`'s unreleased work as if it were released. The site follows the latest release;
  anything only on `main` is marked as such or left out.

## Constraints

- Same toolchain as the sibling sites: MkDocs with Material 9.7.7, installed in CI from a
  hash-pinned `docs/requirements.txt` generated by
  `uv pip compile docs/requirements.in --generate-hashes --universal --python-version 3.13`;
  `mkdocs build --strict` must pass.
- Actions pinned the way the repository's existing workflows pin them (by version tag, e.g.
  `actions/checkout@v6`).
- `docs/superpowers/`, `docs/plans/`, `docs/native-image-hints.md` and `docs/requirements.*` are
  excluded from the site (`exclude_docs`). `specs/` stays out of the site and out of Context7.
- The repository's license-header check must still pass (exclude the generated
  `docs/requirements.txt` if the check covers `.txt`).
- The existing `docs/architecture.svg` is reused.
- Writing style matches the owner's other guides (who, occlude): plain, direct sentences; short
  paragraphs; code that compiles against the documented version; no emoji, no marketing tone.

## Approaches considered

- **A. Rebuild the README as a site.** Split and edit existing material into pages. Fast and
  faithful, but only as complete as the README: backends stay table rows.
- **B. A full manual (chosen).** A, plus new material: a page per backend, choosing a backend,
  testing, operating. Every page verified against the code.
- Generating most pages from Javadoc was dismissed: the Javadoc is reference, not explanation.

## Site structure

Navigation (tabs: Home, Guides, Primitives, Backends, Reference):

- **Home** (`index.md`): what Substrate is, the three primitives in a sentence each, the
  backend matrix at a glance, links onward.
- **Getting Started**: dependencies (BOM, one backend), a first Atom/Journal/Mailbox in a
  Spring Boot app and in plain Java, the in-memory fallback.
- **Concepts**: subscriptions, lifecycles, `Snapshot<T>` and staleness tokens, `JournalEntry<T>`,
  TTL (and how it differs by primitive), eager `create()` vs lazy `connect()`, `TypeRef` for
  generic types, notifiers and how cross-node wake-ups work.
- **Primitives**: one page each for Atom, Journal and Mailbox: what it is for, its API, its
  semantics and edge cases, worked examples.
- **Backends**:
  - Overview and **choosing a backend**: the support matrix (verified from code, including
    notifier support), mixing a storage backend with a separate notifier, trade-offs.
  - One page per backend: Redis, PostgreSQL, Hazelcast, NATS, MongoDB, DynamoDB, Cassandra,
    etcd, RabbitMQ, SNS/SQS, plus the in-memory backend. Each: the dependency, what it provides,
    what it needs (server version, schema or setup, permissions), its properties and defaults,
    how each primitive maps onto it, guarantees and limits, local development.
- **Guides**: Encryption at rest (`substrate-crypto`, shared key, `SecretKeyResolver` and
  rotation, wire format), Testing (in-memory, Testcontainers), Operating in production
  (sweeping, TTL, monitoring and failure behaviour as the code supports it), Native images
  (only if the code ships the hints; otherwise left out).
- **Reference**: Configuration (every `substrate.*` property, from the `@ConfigurationProperties`
  classes), Exceptions, Design principles, API (Javadoc), Changelog (link).

The README becomes the front door: what Substrate is, a short quick start, the backend matrix,
and a link to the site. Material that moves to the site is removed from the README.

## Look

The owner's shared site style: Material with Source Sans 3 and JetBrains Mono, the shared
`jwcarman.css` from who and codec, and a small `substrate.css` for Substrate's own accent colour,
light and dark palettes. No logo exists; the site uses the name as its wordmark. (Builder's call
on the accent colour; keep it restrained.)

## Agents and discovery

- mkdocs-llmstxt 0.5.1 in the pinned requirements, with sections mirroring the navigation and a
  one-line "read this for…" description per page, and a short `markdown_description` with the
  Maven coordinates and changelog link.
- `context7.json` at the repository root, in the shape of codec's: `folders: ["docs"]`, excluding
  `docs/superpowers`, `docs/plans` and the stylesheets, a descriptive title and description, and
  three to five rules from the docs. After merge, the owner's Context7 library `/jwcarman/substrate`
  is added, claimed and set to read `context7.json`, and 0.10.0 is added as a version.

## Javadoc

An `api-docs.yml` workflow modelled on codec's: on release, build the aggregated Javadoc and keep
each release's copy on an `api-docs` branch; the docs workflow copies it into the site under
`/api/`. Navigation links `API (Javadoc)` to `/api/latest/`.

## Delivery

- `main` has no branch rules, so the work lands on `main` directly, in a few reviewable commits
  (site skeleton and workflow; content; README trim; Context7), pushed once the owner has
  looked at the built site.
- GitHub Pages is enabled for the repository with the GitHub Actions source.
- The site is built locally with `--strict` before pushing, and every page is read once for
  accuracy against the code.

## Left to the builder

Page wording and examples; the accent colour; how deep each backend page goes where the backend
is simple (etcd, SNS); whether a short FAQ earns a page.
