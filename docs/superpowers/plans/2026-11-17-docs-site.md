# Substrate Documentation Site Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish a complete, accurate MkDocs Material manual for Substrate at
`https://jwcarman.github.io/substrate/`, with Javadoc, `llms.txt` and a Context7 index.

**Architecture:** Markdown pages under `docs/`, built by MkDocs Material from hash-pinned
requirements in a `docs.yml` GitHub Actions workflow and deployed to Pages; an `api-docs.yml`
workflow keeps each release's Javadoc on an `api-docs` branch that the docs build copies under
`/api/`. Every fact is checked against the code; the README shrinks to a front door.

**Tech Stack:** MkDocs 1.6.1, Material 9.7.7, mkdocs-llmstxt 0.5.1, uv, GitHub Actions, Pages.

**Spec:** `docs/superpowers/specs/2026-11-17-docs-site-design.md`

## Global Constraints

- `mkdocs build --strict` passes after every task.
- Requirements: `docs/requirements.in` lists `mkdocs-material==9.7.7` and
  `mkdocs-llmstxt==0.5.1`; `docs/requirements.txt` is generated with
  `uv pip compile docs/requirements.in --generate-hashes --universal --python-version 3.13 -o docs/requirements.txt`
  and installed in CI with `pip install --require-hashes --only-binary ':all:' -r docs/requirements.txt`.
- `exclude_docs`: `/superpowers/`, `/plans/`, `/native-image-hints.md`, `/requirements.*`.
- Actions pinned by version tag, as the repository's workflows already are (`actions/checkout@v6`).
- Look: Material, Source Sans 3 / JetBrains Mono, `docs/stylesheets/jwcarman.css` copied verbatim
  from codec, plus `docs/stylesheets/substrate.css` for the accent; light and dark palettes.
- Content follows the latest release, 0.10.0; anything only on `main` is marked "not yet
  released" or left out. Compare against `git diff 0.10.0..main` when in doubt.
- No guarantee, property, default, class or method appears on a page unless the code shows it.
- No changes to Java code. Doubts or bugs found while writing go into
  `docs/superpowers/plans/2026-11-17-docs-site-findings.md` (not published) for the owner.
- Style: plain, direct sentences; short paragraphs; no emoji, no marketing tone; Java snippets
  use real signatures.
- `./mvnw -q -B -Plicense license:check` (if the profile exists) still passes.

## Review Focus

1. A backend page that claims a primitive or notifier the module does not implement (the README
   matrix and a quick scan already disagree on RabbitMQ, SNS and notifiers) → Task 4's matrix
   check.
2. A property name or default that is not in the `*Properties` classes → Task 7's property check,
   run over every page.
3. A Java snippet using a method or type that does not exist at 0.10.0 → Task 9's snippet check.
4. TTL or delivery semantics stated more strongly than the code implements (e.g. exact expiry,
   exactly-once) → each primitive and backend page cites the class whose behaviour it describes;
   checked in Task 9.
5. Material copied from the README that the README itself gets wrong → every moved section is
   re-checked against code, not trusted (Tasks 2–6).

### Task 5: One page per backend

**Files:** the ten `docs/backends/<name>.md` pages.

Each page, from that module's code: dependency; primitives and notifier it provides (from Task
4's table); what it needs (server version as tested in the module's Testcontainers tests,
schema or setup it creates or expects, permissions); its properties and defaults (from its
`*Properties` class); how each primitive maps onto the store; guarantees and limits; local
development (the container its tests use). Simple backends (etcd, SNS) stay short.

- [ ] **Step 1:** Write the pages two or three at a time, building with `--strict` after each batch.
- [ ] **Step 2:** Commit `docs: a page per backend`.
